# Triage

Turn every idea, report and meeting finding into a contract, and move issues
on the project issue tracker through its states. The tracker, its queries
and what each label means are in the
[issue tracker doc](../../../docs/agents/issue-tracker.md); read its
[Labels](../../../docs/agents/issue-tracker.md#labels) and
[Contract](../../../docs/agents/issue-tracker.md#contract) sections first.

Write to the issue tracker once a maintainer agrees on the outcome. Until
then the work lives in the session, which is resumed if it stops.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs

## Labels

Every triaged issue carries exactly one kind and one state from
[Labels](../../../docs/agents/issue-tracker.md#labels), which says what each
label means and who sets it. Keep an issue's existing kind unless it is
wrong.

If state labels conflict, flag it and ask a maintainer before doing anything else.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once someone answers. A maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

A maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42"
- "I have an idea: the events page should show which events are fully booked"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Run the queue queries in
[Triage](../../../docs/agents/issue-tracker.md#triage) and present three
buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with a reply from anyone since the last triage notes**: needs re-evaluation.

Show counts and a one-line summary per item. Let a maintainer pick.

## Triage an issue or an idea

1. **Gather context.** For an issue, read it in full (body, comments, labels, assignees, author, dates) and parse any prior triage notes so you don't re-ask resolved questions. For an idea, a maintainer's own words are the request. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks: (a) **redundancy**: search the codebase for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, an issue is an already-implemented `wontfix` (step 5); an idea stops there. (b) **overlap and prior rejection**: search the tracker as [Searching before publishing](../../../docs/agents/issue-tracker.md#searching-before-publishing) says, and surface each open issue that overlaps or contradicts this one and each earlier rejection that resembles it.

2. **Recommend.** Tell a maintainer your kind and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). When the issue is assigned to someone outside the session, name the assignee and say that [Assignees](../../../docs/agents/issue-tracker.md#assignees) applies. Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps; to run the site, follow [Setup and startup](../../../docs/development/local-environment.md#setup-and-startup). Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round of questions at a time, sharpening domain terms and capturing glossary and ADR text as decisions land. The contract carries that text as [Decisions](../../../WAY_OF_WORKING.md#decisions) says.

5. **Apply the outcome** a maintainer agrees on, routed by size as [Choosing a route](../../../WAY_OF_WORKING.md#choosing-a-route) says. For an idea, file the outcome as a new issue with a kind label; an idea that is rejected or already implemented is not filed.
   - `ready-for-agent`, for one ticket: write an agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)), as a comment on an issue or as the body of a new one. Set its blockers as native dependencies, as [Dependencies](../../../docs/agents/issue-tracker.md#dependencies) says.
   - More than one ticket: read and follow [`to-spec`](../to-spec/SKILL.md), then [`to-tickets`](../to-tickets/SKILL.md), in this session. When the work started as an issue, the spec's Further Notes link back to it; after the spec is published, close that issue as a duplicate of the spec.
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`, when an answer must come from someone not in the session: post triage notes (template below). Questions a maintainer in the session can answer are settled in the session instead.
   - For `wontfix`, close the issue as not planned, with the comment depending on *why*:
     - **Already implemented**: the change already exists in the codebase. Point to where it lives.
     - **Rejected (bug)**: give a polite explanation, then close.
     - **Rejected (enhancement)**: give the reasoning in the closing comment, so a later search finds it as an earlier rejection, then close.
   - `needs-triage`: apply the label. Optional comment if there's partial progress.

## Quick state override

If a maintainer says "move #42 to ready-for-agent", trust them and apply the label directly. Confirm what you're about to do (label changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@who-must-answer):**

- question 1
- question 2
```

Address the notes to whoever must answer, which may not be the reporter. Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

An idea that stopped before anything was filed is resumed in its session. If prior triage notes exist on an issue, read them, check whether anyone has answered the outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
